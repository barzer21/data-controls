# ‏ביקורת ארכיטקטורה ואיכות קוד

‏תאריך: 16.11.2026. בסיס הסקירה: commit ‏`86e0d4d` והקוד שנמצא בתיקיית העבודה. כל הממצאים פתוחים לבדיקה ולהחלטה; אין בדוח סימון של תיקונים שבוצעו בעקבותיו.

## ‏A. הערכה מסכמת

‏הפרויקט בנוי כמערכת קטנה עם חלוקת אחריות סבירה, ולא נדרש שכתוב. מנוע הבקרות גנרי ומבוסס מטא־דאטה; הגדרת הבקרה נפרדת מתרגום SQL ומההרצה. מסלולי יצירה ידנית ו־AI משתמשים באותו מנוע. בפרונטאנד קיימים רכיבים משותפים אמיתיים, ובפרט `RuleResultsComponent` שכבר משמש את שני תהליכי ההרצה ומכיל את המסננים והטבלה.

‏הבעיות המרכזיות הן אובדן דיוק מספרי במעבר דרך JavaScript, חוסר אחידות בחוזים ובטיפול בשגיאות, הגדרות התנהגות שמועתקות בין רכיבים, ומסמכי מעקב שאינם מתארים באופן עקבי את המצב הנוכחי. בבנייה התקבלו גם אזהרות אבטחה מאומתות על תלות עקיפה. לא זוהתה תקלה ברמת Critical, ולא הוכח נתיב לניצול החולשה מתוך היישום.

### ‏חוזקות שכדאי לשמר

- ‏`RuleDefinition` ועץ AND/OR מאפשרים להוסיף בקרות בלי לכתוב SQL ייעודי לכל בקרה. שמות הטבלאות מגיעים מהקטלוג ולא מתנאים כגון „אם עובדים אז…”. קוד חישוב גיל הוא הרחבה לסוג שדה מחושב, ולא שאילתה קבועה לבקרה מסוימת.
- ‏`RuleValidator`, ‏`RuleSqlCompiler`, ‏`RuleExecutor` ו־`RuleExplanationService` מחזיקים אחריות שונה ומוצדקת. ההסברים מתבססים על תוצאת SQL ולא מחשבים מחדש את התנאים ב־C#.
- ‏ערכים נשלחים כפרמטרים; מזהים נלקחים מקטלוג מאומת ונעטפים. ההרצה עוברת למשתמש DB מוגבל בחיבור ללא pooling, ללא ניסיון חוזר בחיבור בעל הרשאות כתיבה.
- ‏`RuleService` משתמש ב־EF Core לשמירת הגדרות בלבד. אין צורך להוסיף Repository כללי מעל EF Core.
- ‏רכיבי הטבלה, המסננים, בחירת הנתונים והצגת התנאים משותפים. חיפוש אינו שומר בקרה, בקשות ישנות מבוטלות, ובפתיחה מחדש של תוצאות המסננים מתאפסים.
- ‏השימוש ב־`OnPush`, ב־signals, ב־`switchMap` וב־`takeUntilDestroyed` עקבי ברוב הזרימות שנבדקו. לא נמצאה דליפת subscription מוכחת.
- ‏קיים כיסוי בדיקות משמעותי של תנאים מקוננים, NULL, תאריכים, פרמטריזציה, סינון, ביטול בקשות ואישור הצעות AI.

### ‏מה לשתף, לפצל, למזג או להסיר

- ‏**לשתף:** פענוח שגיאות, הגדרות אופרטורים, פונקציות מטא־דאטה ופרוטוקול אישור עזיבה. לא כל אחד מהם צריך להיות service עם DI; ברובם פונקציות טהורות או helper מקומי מספיקים.
- ‏**לפצל בהדרגה:** `RuleEditorComponent` מחזיק גם תזמור API וגם UX. קודם מוציאים parsing ופונקציות טהורות ומסירים את ה־round-trip המיותר. רק אם נותר תזמור מסובך, שוקלים facade ברמת רכיב; 274 שורות לבדן אינן הצדקה להפשטה.

- ‏**להסיר:** לא זוהתה קומפוננטה פעילה שהיא קוד מת. ארבעת רכיבי העמוד מופיעים ב־routes גם אם אין תג שלהם ב־HTML. `RuleExecutionSessionService` ומעטפת תוצאות הטיוטה אינם קיימים בקוד הנוכחי ואין להציגם כמשימה פתוחה. אפשר להסיר תנאי pre-validation בעורך רק לאחר יישור השגיאות והבדיקות; לא להסיר הגנות שרת.
- ‏**CSS:** שיתוף mixin/class בלבד היכן שהעיצוב וההתנהגות באמת זהים. אין צורך בקומפוננטת „מסגרת” חדשה לכל כרטיס דומה.

## ‏D. ארכיטקטורת יעד לפרונטאנד ולבקאנד

### ‏פרונטאנד

‏להשאיר את מבנה `features/rules`, ‏`shared` ו־`core`. לרכז ב־core/api parsing של תגובות שגיאה ובחוזה משותף את הטיפוסים והאופרטורים; למקם פונקציות מטא־דאטה מחוץ למודל של עורך מסוים. אין הצדקה ל־NgRx, לירושת בסיס בין עמודים או לשירות תוצאות נוסף רק בגלל קיום שני מקומות תצוגה.

‏לשמר את הבידוד בין initialResult לבין הרצה ראשונית: טיוטה שכבר הורצה אינה צריכה להריץ שוב עם יצירת רכיב התוצאות. ניסיון חוזר של הרצה משתמש בעותק המוצג ובמסננים הפעילים; ניסיון חוזר של טעינת בקרה נשאר בעמוד.

### ‏בקאנד

‏להשאיר API יחיד ולא לפצל למיקרו־שירותים נוספים. השרשרת המתאימה היא:

```text
Controllers → RuleService → EF Core → Rules
Controllers → RuleExecutionService → RuleSqlCompiler → RuleExecutor
                                    RuleValidator      RuleExplanationService
                                    Metadata resolver
AiProposalsController → IAiRuleProposalProvider → Python
                                             → RuleValidator
```

‏resolver משותף של מטא־דאטה יכיר שדות וקשרים בלבד. מצב alias, פרמטרים וראיות להסברים יישאר בתוך קומפילציה אחת. אין להפוך את תוצאת הקומפילציה למצב משותף בין בקשות.

‏ה־lifetimes הנוכחיים מתאימים לשימוש שנבדק: AppDbContext ו־RuleService הם scoped; הספק של הקטלוג והמנועים ללא מצב בקשה הם singleton; הקומפיילר והמאמת יוצרים מצב traversal לכל פעולה; מתאם Python נוצר דרך HttpClient. אין כרגע singleton שמחזיק AppDbContext. `RuleExecutionService` הקצר מוצדק כי הוא מרכז את מסלול ההרצה המשותף; אורכו אינו סיבה למחיקה.

‏להפריד את אפשרויות JSON של חוזה הבקרה מ־MVC באופן מדורג. אפשר להשאיר persistence model של `SavedRule` נפרד מ־RuleDefinition ומ־response DTOs כפי שהוא כיום. מחלקות Employee/Department ב־EF מייצגות את נתוני הדוגמה ואינן מעידות שהקומפיילר מקודד אליהן.

### ‏Python והחוזה הבין־שפתי

‏לשמר שירות mock נפרד וממשק ספק ב־‎.NET. דוגמאות mock יכולות להיות קבועות; האיסור במטלה הוא על מנוע SQL ייעודי לכל בקרה, לא על fixtures של הדגמת AI. יש ליישר את החוזה ואת מקור הדוגמאות ולשמור אימות שרת. אין לשתף את כל קוד האימות של ‎.NET עם Angular/Python בכוח; checks בצד לקוח מיועדים למשוב, ושרת נשאר סמכות.

### ‏SQL, הרשאות וגבולות שלא צריך לשנות כחלק מניקוי

‏הפרמטריזציה, quoting, אימות הקטלוג מול PK/FK אמיתיים, LEFT JOIN והמעבר למשתמש הקריאה הם מנגנונים חיוביים. פרויקט אינו מוכן אוטומטית לייצור: משתמש החיבור הרגיל עדיין בעל הרשאות שמירה ו־IMPERSONATE. אין במטלה דרישת התחברות, multi-tenancy או RBAC, ולכן היעדרם אינו מסווג כחסר חובה.

‏השוואות NULL, collation של טקסט ותאריכים ללא שעה הן התנהגות מתועדת ומכוסה בחלקה בבדיקות. תוצאות מוגבלות ל־100 בממשק ו־500 ב־API, אך הספירות מחושבות לכל הנתונים המתאימים. היעדר pagination מלא לתוצאות, snapshot טרנזאקציונלי ומנגנון התנגשות עריכות מתועד כמגבלה; אין להפוך אותו לרגרסיה שלא הוכחה. COUNT/חלון ועמודות ראיות עשויים להיות יקרים על DB גדול, אך לפני שכתוב נדרשת מדידת execution plan ועומס.
