# Generic create/edit rule editor

Implemented 2026-11-12. Assignment scope: GEN-02/03, RULE-01..05, TECH-07, EXEC-05 and UX-01. Modal placement, native dialog, metadata traversal bounds and inline draft preview are design choices (D-024), not additional assignment requirements.

Updated 2026-11-15 (D-026/D-027): saved-rule editing uses `/rules/:id/edit?page=...`, a full page within the application shell. AI creation and proposal review use `/rules/ai/new` from the sidebar. Manual creation now uses `/rules/new?page=...` from the sidebar too, without a dialog. The form, validation, draft execution and result preview remain shared rather than duplicated. The brand text now has explicit light default/visited colors on the dark rail.

Self-comparison follow-up: a field is excluded from its own right-side selector using its case-insensitive business ID plus full relationship path. Root and related fields with the same ID remain distinct. If there is no other field of the same type, the field-operand choice is disabled instead of falling back to the left field. Existing self-comparisons are not silently rewritten; their right selector requires a different field, and the server rejects validation/save/execution with `sameFieldComparison`. The backend compares references case-insensitively and treats null/empty root paths equivalently.

Follow-up verification: build, 86 Angular tests, 48 compiler checks and 46 HTTP validation checks passed. Native Edge verified that a department's active flag cannot appear on both sides while the employee's active flag remains available. No database schema or stored definitions were changed for this restriction. ## UI and boundaries

Cleanup (2026-11-15): page-based components are now named `rule-editor` / `RuleEditorComponent` and `ai-rule-creator` / `AiRuleCreatorComponent`. The obsolete dialog names, constant template expressions and prototype were removed. `core/routing` centralizes the list-page bounds and post-save return behavior for manual and AI creation. The reusable browser check is `frontend/tools/check-rule-workflows.mjs`. Build, 111 Angular tests, unused-import/local checks and native desktop/mobile browser checks passed. Python syntax, the five supported proposal scenarios and the HTTP route were also checked; no backend/database behavior was changed. See [CODE_GUIDE.md](CODE_GUIDE.md) for the current code map.

- The approved Heebo design is implemented in the shared editor: numbered sections for entity, conditions and rule details; icon cards for metadata entities; and an Edit/Read switch showing the current unsaved draft without extra API calls. Changing a card still requires in-page reset confirmation. The read view labels unsaved changes and retains save/run/AI approval behavior.
- `EntityPickerComponent`, `RuleOverviewComponent`, `RuleSummaryComponent` and `UiIconComponent` provide separate presentation boundaries. The recursive editor keeps every operator, typed constant, compatible field operand, NULL check and nesting limit. Constant/field selection is visually secondary rather than removed. Summaries retain explicit group boundaries and related-field labels; they do not flatten mixed AND/OR trees.
- Heebo is bundled under `frontend/public/fonts/heebo` with its OFL license and loaded by local `@font-face` (no external font service or additional package). Responsive layouts stack the summary below the form, and the existing stable scrollbar gutter remains enabled.

- New Rule appears in the sidebar alongside the library and AI creation. Only the current section is marked active. Each saved row has Edit alongside Run; the list no longer mounts a creation dialog.
- Create and Edit navigate to `RuleEditorPageComponent`, which renders the shared form as a normal `main` without a dialog or backdrop. The page has a return action, a sticky action footer and a router departure guard; unsaved navigation requires explicit discard or continuation within the page. All native dialog branches, modal styles and browser unload prompts have been removed at the user's request. Reloading or closing the tab discards unsaved work without a prompt. Requests disable duplicate actions and departure while in flight.
- New rules receive an initial comparison based on the selected metadata entity. Edit fetches the entire saved definition by ID and edits a deep copy, not a list summary. Failed loads cannot submit a blank replacement.
- Name (required, up to 200 characters), description (optional, up to 2,000), business entity and nested condition tree are editable. Changing the entity requires confirming a reset of the old conditions.
- `ConditionEditorComponent` is reusable and recursive. Business fields are discovered from metadata, including outgoing relationship paths bounded to four links. JSON references remain stable while labels are business-facing. Groups support AND/OR, adding comparisons/subgroups and removing children while preserving at least one child. Controls enforce the eight-level bound, and the dialog rejects trees over 100 nodes.
- Comparison options follow field type: equality/inequality and missing/not-missing for all types; ordering for numbers/dates. Right operands can be typed constants or metadata fields of the same type. For related booleans, the user explicitly retained comparison to another boolean field and missing/not-missing checks; the latter can detect a missing relationship. Constant boolean values use yes/no choices. Event handlers reject unavailable operators and non-boolean boolean values; invalid saved values show a placeholder rather than silently displaying No. Controls are disabled until a valid field is selected. Number/boolean/date inputs produce JSON numbers/booleans/ISO dates. NULL operators omit the right operand. Grouping does not silently change existing selections; NgModel keeps select display synchronized when nested views are recreated.

## Save and run

Save-button correction (2026-11-15): the footer now calls `perform('save')` explicitly in both edit and read modes. Previously the edit-mode click expression returned false, cancelling the native submit default before validation or persistence could run. Enter submission remains available through the form. Success navigates to the library, scrolls to the top and displays the existing success notice. Failure retains the draft and focuses the error summary. Router tests use actual button clicks for manual creation, updates and approved AI proposals; Edge fixtures exercise failed PUT/retry, successful PUT, reopened persisted data, POST creation and a visible success notice.

Both actions first POST the current definition to `/api/rules/validate`. The server remains authoritative; semantic messages and business condition numbers are displayed without internal SQL details. Input remains available after validation/network failures.

- Save explicitly POSTs `/api/rules` for a new rule or PUTs `/api/rules/{id}` for edits. AI creation adds its creation-origin query flag. Saving never runs a rule. Success returns to the library with a success notice. Creation queries the count to navigate to the last page (API sorts by ID), falling back to the return page if the count request fails; edit preserves the current list page.
- Run submits only the current draft snapshot to the existing execution endpoint. It never POSTs a saved definition or PUTs an existing one. The editor shows the exact executed conditions and reuses the generic result table/count/empty/truncation states. Search and typed column filters operate on that executed snapshot, including unsaved changes, using the same controls as the dedicated results page. Edits clear previous preview data and criteria and cancel pending filtering. Run neither closes the editor nor discards unsaved work.
