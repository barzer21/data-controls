# ‏תכנון משימת הרשות — הצעות יזומות לבקרות איכות נתונים

## ‏מטרה והיקף

‏המערכת תנתח את מבנה הדאטה בייס ואת משמעות השדות והקשרים, ותציע בקרות בלי שהמשתמש יצטרך לתאר מראש מה לבדוק. לדוגמה, זיהוי תאריכי תחילת וסיום העסקה יאפשר להציע בדיקה שסיום ההעסקה אינו מוקדם מתחילתה.

‏זהו תכנון בלבד. כיום שירות Python מחזיר הצעת mock לפי תיאור שהמשתמש מזין. ביכולת המתוכננת המשתמש ילחץ על „הצע בקרות לנתונים שלי”, ויקבל עד חמש הצעות לבדיקה. הן לא יישמרו ולא ירוצו אוטומטית.

## ‏המידע לניתוח

‏שרת ‎.NET יעביר לשירות Python מידע מתוך הקטלוג העסקי המאושר:

- ‏שמות עסקיים, מזהי שדות, סוגי נתונים וקשרים בין הטבלאות.
- ‏תיאורים עסקיים ואפשרות לערך חסר, אם הוגדרו. מידע זה דורש הרחבה של הקטלוג הציבורי הקיים.
- ‏התנאים שהמנוע תומך בהם והגדרות הבקרות הקיימות, כדי למנוע הצעות לא נתמכות או כפולות.

‏הניתוח יוגבל למידע שבקטלוג. לא יועברו רשומות עסקיות, פרטי התחברות או מיפויי SQL, ולא יינתן למודל חיבור ל־DB.

## ‏זרימת העבודה

1. ‏המשתמש בוחר נתונים לניתוח, למשל עובדים ומחלקות, ומבקש הצעות.
2. ‏‎.NET מכין את המידע המאושר ושולח אותו ל־Python, שמפעיל mock או מודל אמיתי.
3. ‏Python בודק את מבנה התשובה. ‎.NET מאמת את ההגדרות באמצעות `RuleValidator` ומסנן הצעות כפולות או לא נתמכות.
4. ‏הממשק מציג כל הצעה עם הסבר. המשתמש יכול לדחות אותה או לפתוח אותה בעורך הקיים.
5. ‏לאחר בדיקה ואישור, המשתמש יכול להריץ טיוטה ולשמור את הבקרה. שינוי בתנאים מאפס את האישור; ההרצה והשמירה מאמתות מחדש את ההגדרה מול הקטלוג הנוכחי.

## ‏מבנה ההצעה

‏כל הצעה תכלול שני שדות בלבד:

| ‏שדה | ‏משמעות |
| --- | --- |
| ‏`definition` | ‏הגדרת `RuleDefinition` הקיימת: שם, תיאור, סוג נתונים ראשי ועץ תנאים |
| ‏`rationale` | ‏מדוע המבנה מצביע על בדיקה שכדאי לבצע, כולל הנחות עסקיות הנחוצות להבנתה |

## ‏השינויים בפרויקט

| ‏רכיב | ‏תוספת מתוכננת |
| --- | --- |
| ‏Angular | ‏מסך הצעות ובחירת נתונים, עם מעבר לעורך ולאישור הקיימים |
| ‏‎.NET | ‏endpoint לקבלת הצעות ושירות שמכין את הקלט, מפעיל את Python, מאמת ומסנן כפילויות |
| ‏Python | ‏חוזי בקשה ותשובה וספק הצעות שאפשר להחליף בין mock למודל אמיתי |
| ‏מטא־דאטה | ‏הוספת מידע עסקי אופציונלי המסייע להסביר את משמעות השדות |

‏ההרצה תשתמש ב־`RuleSqlCompiler` וב־`RuleExecutor` הקיימים. השמירה תשתמש ב־`RuleService` ובטבלת `Rules`, עם סימון מקור AI. אין צורך בטבלה חדשה: הצעות שלא נשמרו יישארו זמניות.

## ‏דוגמאות ומגבלות

| ‏מידע שזוהה | ‏בקרה אפשרית | ‏מה המשתמש צריך לבדוק |
| --- | --- | --- |
| ‏תחילת וסיום העסקה | ‏סיום מוקדם מתחילה | ‏האם יש חריגים עסקיים מותרים |
| ‏פעילות עובד ומחלקה | ‏עובד פעיל במחלקה לא פעילה | ‏האם השילוב אסור בארגון |
| ‏שדה שכר מספרי | ‏שכר שלילי | ‏האם מותר לרשום התאמות שליליות |
| ‏קישור עובד למחלקה | ‏עובד ללא מחלקה | ‏האם השיוך הוא חובה |

‏מבנה ה־DB אינו מספיק לקביעת כלל עסקי. לכן ההסבר חייב לציין הנחות, והמשתמש נדרש לאשר את ההצעה. רק הרצה יכולה לגלות אם קיימות רשומות חריגות בפועל.

- ‏יוצעו רק תנאים שהמנוע תומך בהם; חישובי אגרגציה אינם נתמכים כיום.
- ‏כפילויות יסוננו לפי סוג הנתונים ועץ התנאים, תוך התעלמות מהשם, מהתיאור ומסדר הילדים בקבוצות AND/OR. לא תיבדק שקילות לוגית מלאה.
- ‏יוגבלו גודל התשובה וזמן ההמתנה. שגיאה או תשובה לא תקינה יוצגו למשתמש בלי לשמור בקרות.

## ‏שלבי מימוש ובדיקות

1. ‏הגדרת החוזים ומימוש mock שמחזיר הצעות בהתאם לקטלוג שקיבל.
2. ‏הוספת האימות וסינון הכפילויות ב־‎.NET, עם בדיקות לשדות חסרים, תנאים לא נתמכים ותקלות שירות.
3. ‏בניית מסך ההצעות והדגמת תהליך מלא: הצעה, אישור, הרצת טיוטה ושמירה. בדיקה שאין הרצה או שמירה אוטומטית ושעריכה מאפסת את האישור.
4. ‏בהמשך אפשר לחבר מודל אמיתי, לשמור משוב על הצעות ולהפעיל ניתוח לאחר שינוי בקטלוג. ניתוח נתונים בפועל או מדדים מצרפיים ידרוש תכנון נוסף של פרטיות, הרשאות וביצועים.
